# DECISIONS.md  (about 150-200 words in total - plain language, your own words)

1. **Indexes.** I created four indexes: (a) a unique index on `employees.emp_code` — this enforces uniqueness at the database level so concurrent duplicate creates get a DuplicateKeyError instead of both succeeding; (b) a compound unique index on `attendance_logs.(emp_code, date)` — this enforces one record per employee per day and supports lookups by emp_code+date for punch-out and regularization; (c) a descending compound index on `attendance_logs.(date DESC, emp_code ASC)` — this serves the attendance list endpoint's sort order without an in-memory sort; (d) a single-field index on `attendance_logs.date` — this speeds up the analytics pipelines that filter by date range. I considered indexing `status` but rejected it because status has very few distinct values (low cardinality), so MongoDB would rarely benefit from it.

2. **Punch-in race.** Both requests pass the employee lookup. Both call `insert_one` with the same `(emp_code, date)`. The compound unique index guarantees exactly one insert succeeds. The other raises `DuplicateKeyError`, which my code catches and returns 409. No check-then-insert pattern is used.

3. **Ties.** I use MongoDB's `$setWindowFields` with `$rank` which implements standard competition ranking — tied employees share the same rank and the next rank is skipped (1, 2, 2, 4). The `limit` filter is applied after ranking (`rank <= limit`), so if two employees tie at the cutoff rank, both are returned. The result may have more rows than `limit`.

4. **Headcount.** The department summary queries the `employees` collection separately with `joined_on <= last_day_of_month`. This counts every employee in the department regardless of whether they have attendance logs. The attendance aggregation uses `$lookup` to join logs to employees for the department field, but headcount comes from the employees query, not from the logs.

5. **One thing you would change:** I would add a compound index on `(emp_code, date, status)` and partition the attendance collection by month using time-series or sharding. At 100x data (~10M records), the current single-collection approach with skip-based pagination becomes slow for deep pages. I would switch to cursor-based pagination (keyset pagination using the last seen `(date, emp_code)`) and consider pre-aggregating monthly summaries into a separate collection updated on each write.
